# Раскладка: правильное число изделий на листе и корректное превью

## Проблема

На скриншоте: листовка А5 (148×210), печатный 460×320, закупочный 640×920 → движок выдаёт **2 шт/лист** (1×2) и 655 печатных листов на тираж 1000. По факту А5 на SRA3 (320×460) штатно ложится **4 шт/лист** (2×2). Перепроверь и устрани разницу.

## Корень бага

В `layoutVariants` (src/lib/calc/engine.ts) перебираются только две ориентации **изделия**, но печатный лист всегда фиксирован как `printW × printH`. Из-за асимметрии полей (`marginTop=5`, `marginBottom=12` — захват) ориентация листа влияет на результат:

- Лист 460×320 (как из справочника): availH=320−5−12=303. 2 ряда A5 повёрнутого нуждаются в 2×154=308 → не лезет → **2 шт/лист**.
- Лист 320×460 (тот же лист «портретно»): availH=460−5−12=443, 2 ряда A5 неповёрнутого = 2×216=432 → **4 шт/лист** ✓.

Печатный лист физически один и тот же — захват можно расположить по любой стороне, поэтому движок обязан проверять обе его ориентации.

## Что меняем

### 1. `src/lib/calc/engine.ts` — `layoutVariants`

Перебирать **4 комбинации** (rotated product × rotated sheet) вместо 2. Для каждого валидного варианта возвращать `LayoutResult` с фактической ориентацией листа в `printFormat` (если победила «портретная» — `printFormat = { width: H, height: W }`). Победителя выбираем по тем же правилам (max items, min waste).

### 2. `src/lib/calc/types.ts` — `LayoutResult`

Поле `printFormat` уже есть и теперь содержит ориентацию, в которой лист реально лежит. Никаких новых полей не нужно — превью читает width/height из `printFormat`.

### 3. `rankPairs` / `bestPair`

Логика не меняется: они уже проходят через `layoutVariants`. Дедуп ключ оставить по исходной паре `(p.print.width, p.print.height)`, чтобы один и тот же реальный лист не дублировался в альтернативах из-за перевёрнутой ориентации.

### 4. Превью `LayoutPreview` / `SheetSvg`

Сейчас компонент рендерит по `layout.printFormat.width/height` — после правки это уже будет нужная ориентация, дополнительных изменений по геометрии не требуется. Проверить:
- подпись «460×320 мм» в шапке отрисовки и в режиме «Авто» / «Вручную» совпадает с реальной ориентацией;
- `MiniSheet` для альтернатив берёт `printW/printH` из альтернативы — пробросить ориентированные значения (`a.layout.printFormat.width/height`), а не исходную пару.

### 5. Калькулятор `Calculator.tsx` — отображение

В блоке параметров шага «Раскладка» строка «ПЕЧАТНЫЙ ФОРМАТ 460×320» должна показывать ориентацию из `result.layout.printFormat`, а не выбранную пару. То же — для строки «Печатный … Закупочный …» в правой панели «Геометрия».

В режиме «Вручную»: селект печатного формата показывает пару как в справочнике (460×320), но под раскладкой выводим badge «лист уложен 320×460» если движок развернул его — чтобы пользователь видел, что произошло.

### 6. Тесты `engine.test.ts`

Добавить:
- `A5 (148×210) на 460×320 → itemsPerSheet === 4, cols=2, rows=2` (с любой ориентацией листа).
- `A6 (105×148) на 460×320 → ≥9 шт/лист`.
- Регрессия: стикер 90×50 на 320×460 не теряет шт/лист после правки.

### 7. Что НЕ меняем

- DEFAULTS (margins/bleed) не трогаем — реальные значения корректны для офсета.
- Логику «свой/чужой оборот», приладку, цены — не трогаем.
- Справочники, RLS, схему БД — не трогаем.

## Ожидаемый результат

Для кейса со скриншота (А5, 460×320, тираж 1000):
- `шт/лист`: 2 → **4**
- `печатных листов`: 655 → ~**400** (250 net + 150 приладка)
- `закупочных листов`: 164 → ~**100** на 640×920 (вложение 4 печатных в закупочный)
- Себестоимость и «Δ к авто» пересчитаются автоматически.
